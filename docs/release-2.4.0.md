# 工时账本 2.4.0 发布计划与验收

- 版本：2.4.0
- 日期：2026-10-28
- 基线：2.3.0（163 个单元测试、Capacitor 8、Android API 36）
- 主题：**把每一帧和每一份数据都当回事**

## 1. 为什么是 2.4

2.3 把结构拆开、把派生计算收敛到一次遍历之后，代码已经能读、能测。但对着 2.3 的产物做了一轮通读，仍有五处「知道不对但还没动手」的地方：

1. **动画带着整页重算**。`useAnimatedNumber` 是页面级 hook，620ms 的滚动会触发约 37 次重渲染。首页会连带重算本周概览，统计页会连带重算收入预测与排班对账，年度复盘更是在滚动期间反复重建 12×31 的热力图与按日索引。这是当前最容易被感知的卡顿来源。
2. **统计页的派生数据没缓存**。2.3 已经把周期区间、图表点、班次构成收进一个 `useMemo`，但「本月收入预测」与「排班对账」是在渲染体里直接调用 `buildMonthForecast` / `buildPlanReconciliation` 的——两者都要过滤全量记录与排班。恰好它们和动画在同一个组件里。
3. **损坏数据被静默吞掉**。`readJson` 解析失败时返回空数组，界面看起来「数据没了」；用户随手记一班，写盘就把空数组 + 新记录写回存储，原始内容彻底消失。2.3 只是避免了「挂载即回写」，没有给用户任何挽救路径。
4. **样式与统计页仍然过大**。`index.css` 6972 行，`Stats.tsx` 740 行，改一处都要在长文件里翻。
5. **取整与符号各写各的**。`Math.round(x * 100) / 100` 散落在 11 个文件里，涨跌符号有的用 `-`、有的用 `−`，纯文本工资条导出后可能因字体缺字显示成方框。

2.4 不加新功能，把这五件事收干净。数据格式、存储键、备份版本、计薪口径全部不变。

## 2. 范围

| 方向 | 内容 | 收益 |
| --- | --- | --- |
| 性能 | 新增 `AnimatedValue`；统计页预测/对账 `useMemo`；年度复盘一次性计算 | 动画期间只重渲染一个文本节点 |
| 结构 | `statsRange.ts` + `components/stats/*`；`index.css` → `styles/*.css` | 统计页 740 → 402 行；样式按页定位 |
| 一致性 | `num.ts` 的 `round2`；`formatSignedMoney` / `formatSignedCount` / `formatSignedDuration` | 一处改精度，全站一致 |
| 健壮性 | 损坏数据恢复副本 + 导出入口；CSV 行数上限；非法日期兜底 | 少一类不可逆的数据丢失 |
| 测试 | `statsRange` 12 个用例，CSV / 存储 / 日期边界若干 | 163 → 182 |

### 明确不做

- 不改 localStorage 键名、不改备份 `version`：2.3 与 2.4 的数据可互换。
- 不引入状态管理库、不引入 React Compiler：本轮瓶颈已经定位到具体组件，不需要换范式。
- 不做虚拟列表：首页已按 10 天分批渲染，先解决「重复计算」比「减少节点」收益大。
- 不重写 `utils.ts`：它现在是一组展示格式化函数，拆分只会增加 import 跳转；等它继续长到 800 行以上再拆。
- 不动动效参数：动画时长、缓动曲线保持不变，本版只改「谁来重渲染」。

## 3. 设计要点

### 3.1 把动画关进一个文本组件

```tsx
<AnimatedValue value={summary.earnings} resetKey={rangeKey} />
```

- 动画状态（`useState` + `requestAnimationFrame`）从页面组件搬进 `AnimatedValue`，每帧只更新这一个节点；
- `resetKey` 语义不变：切换月份 / 周期时直接切值，不播放滚动；
- 传 `format` 可显示百分比（统计页目标完成率用 `format={Math.round}`）；
- `prefersReducedMotion()` 时 `useAnimatedNumber` 直接返回目标值，组件退化为普通文本。

### 3.2 派生数据算一次

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 统计页 | 每次渲染调用 `buildMonthForecast` + `buildPlanReconciliation` | `useMemo`，`now` 对齐到分钟 |
| 年度复盘 | 每次渲染重建 `summary` / `heatmap` / `days` / `dayMap` | 一个 `useMemo`，依赖 `[records, year]` |
| 首页 / 日历 | 金额滚动期间整页重算 | 不再因动画重渲染 |

`now` 对齐到分钟而不是直接用 `useClock()` 的 `Date` 对象，是为了让依赖稳定：`isPlanPast` 只关心「到没到点」，秒级差异不影响结果。

实测（合成数据：5 000 条记录 + 200 个排班，Node 22 / 本机）：

| 场景 | 主线程耗时 |
| --- | --- |
| 37 帧 × （月度预测 + 排班对账 + 年度汇总 + 热力图 + 按日明细） | 339 ms |
| 同上，现在只算一次 | 9 ms |

> 这是纯计算的对比，不含 React diff 与样式计算；真实收益还包括少掉的 36 次组件树协调。

### 3.3 损坏数据：先保全，再提示，可导出

```
读取 → JSON.parse 失败
      ├─ 原文写入 shift-ledger.recovery.v2（按 key 去重，同一份只写一次）
      ├─ 派发 shift-ledger:storage-recovery
      └─ 本次读取回退为空集合
界面 → 提示条「本地数据读取失败，原始内容已保留」+「导出副本」
导出 → 下载 recovery.v2 的 JSON，清除该键，不再重复提醒
```

设计取舍：

- **不做自动修复**。无法判断坏在哪一条，猜着修会把「可读的部分」也改掉；保全原文 + 让用户导出，是唯一不丢信息的做法。
- **按内容去重**。同一份坏数据每次启动都会读到，只有内容变化才重写、才再提示。
- **恢复副本也进兜底**。错误边界的「导出原始数据」快照包含这个键，白屏时同样能带走。
- **写失败不阻断**。保全本身可能因配额不足失败，`preserveCorrupt` 内部吞掉异常，读取流程照常返回兜底值。

### 3.4 样式拆分与「逐字节一致」

`index.css` 按原有分节注释切成 20 个连续区间，`index.css` 只留 `@import`，顺序即原顺序。验证方式不是「看起来没变」，而是比对构建产物：

```bash
vite build
# 2.3 产物：dist/assets/index-B79241hj.css（98 298 字节）
# 2.4 产物：同名、同哈希、同字节数 → 级联结果完全一致
```

拆分后每个文件头部有一行说明（属于哪一页、原区间），构建时注释被压缩掉，不影响体积。

### 3.5 数值与符号

- `round2`：非有限数返回 0。以前 `NaN` 会顺着 `Math.round(NaN * 100) / 100` 传下去，最终在界面上显示「¥NaN」。
- `formatSignedMoney` / `formatSignedCount` / `formatSignedDuration`：`+¥120` / `-¥120` / `¥0`，`+3` / `-3` / `0`，`+1 小时 30 分` / `-1 小时 30 分`。
- 减号统一用 ASCII `-`：工资条与年度报告是纯文本，会经系统分享发到微信 / 邮件，排版减号 `−`（U+2212）在部分安卓字体里缺字。

## 5. 后续可改进方向

1. **组件拆分**：`RecordSheet`（419 行）/ `PlanSheet`（458 行）/ `Calendar`（729 行）仍可继续拆；本轮优先处理了「重复计算」，下一轮可以处理「单文件体积」。
2. **IndexedDB**：localStorage 单键 5 MB 上限，记录量再上量级时换引擎；届时写盘队列可从「整集合序列化」改为按记录增量写。
3. **虚拟列表**：记录过万后，首页 `groupByDate` 仍会处理全部记录，可按月分页查询。
4. **诊断面板**：目前只有 `console.error`、错误边界与恢复副本，可把存储异常、写盘失败、导入失败次数记在本机，设置页展示。
5. **交互增强**：日历长按拖选多日、统计页区间对比、导出月报图片（2.2 起列为待办）。
6. **`utils.ts` 再拆分**：等它超过 800 行，或出现第二个消费方时再拆成 `format/`、`record/` 两组。
