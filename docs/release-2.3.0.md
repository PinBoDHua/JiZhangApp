# 工时账本 2.3.0 发布计划与验收

- 版本：2.3.0
- 日期：2026-10-28
- 基线：2.2.0（125 个单元测试、Capacitor 8、Android API 36）
- 主题：**把地基夯实**

## 1. 为什么是 2.3

2.0 把计薪、预测、复盘做深，2.1 补齐动效与手感，2.2 把「算对」和「补记」做顺手。功能面已经够用，但代码结构开始出现两处结构性负担：

- `App.tsx` 1346 行，同时承担浮层状态机、7 个集合的写操作、导入导出和整个页面布局；
- `storage.ts` 607 行，把存储键、迁移、类型守卫、备份解析混在一个文件里；
- 首页 / 日历 / 统计各自用 `filter + reduce` 现算派生数据，同一条记录为了「工时」和「收入」会被计薪两次，统计页的 31 天柱状图甚至会对全量记录过滤 31 次。金额滚动动画每帧都会重渲染，这类重复计算会直接体现为掉帧。

2.3 不加新功能，只做四件事：拆结构、去重复计算、补边界、补测试。数据格式、存储键、备份版本全部不变，用户升级后无感。

## 2. 范围

| 方向 | 内容 | 收益 |
| --- | --- | --- |
| 数据层 | `storage.ts` 拆为 `storage/{keys,guards,backup,index}.ts` | 键/迁移、校验、备份各自独立，对外 import 路径不变 |
| 动作层 | `App.tsx` 拆为 `useSheetController` / `usePlanActions` / `useRecordActions` / `useBackupActions` | 页面只负责组合与渲染，业务规则可按域定位 |
| 派生层 | 新增 `overview.ts`、`search.ts` | 一次遍历按日汇总，组件不再重复计薪 |
| 性能 | 首页 / 日历 / 统计记忆化，`RecordRow` memo 化，写盘策略调整 | 大记录量下翻页、搜索、切周期更顺 |
| 健壮性 | 跨标签页同步、通知深链校验、备份条目上限、环境兜底 | 少一类静默数据覆盖与一类崩溃 |
| 无障碍 | 浮层打开时主区与底栏 `inert` | 读屏与 Tab 不再穿透到背景 |

### 明确不做

- 不改 localStorage 键名、不改备份 `version`，2.3 与 2.2 的数据可互换。
- 不引入状态管理库或 React Compiler：当前瓶颈是重复计算，不是更新粒度。
- 不做虚拟列表：首页已经按 10 天分批渲染，先把派生计算收敛掉收益更大。
- 不做云端同步：跨标签页同步只解决同一浏览器多窗口，不涉及服务器。

## 3. 设计要点

### 3.1 分层

```
组件层  components/*            只做展示与本地交互状态
        App.tsx                 组合、标签页、浮层挂载
动作层  hooks/use*Actions       数据变更、提示、确认、撤销
派生层  overview / search /
        pay / forecast / ...    纯函数，可单测
数据层  storage/                读取 → 校验 → 归一化，写入
```

约定：

- 组件不直接调用 `setRecords` 之类的 setter，也不写 `localStorage`；
- 所有会改变集合的操作集中在动作层，成功后统一 `haptic + notify + closeSheet`；
- 派生层函数不读全局状态、不读时间，时间一律由调用方传入。

### 3.2 一次遍历的派生数据

`summarizeByDate(records)` 把记录按日期汇总成 `{ earnings, minutes, shifts }`：

- 首页：本月汇总、本周对比、每日柱状图、按天分组的合计全部查表；
- 统计页：图表（周 7 天 / 月 28–31 天 / 年 12 个月）先按日汇总再按周期取数；
- 日历：当月收入、每日小计、选中日合计共用一份汇总。

计薪次数从「每条记录 × 字段数」降到「每条记录 1 次」，月视图柱状图从 31 次全量过滤降到 1 次。

### 3.3 写盘策略

`useAppData` 的持久化 effect 会跳过首次挂载：

- 数据刚从存储读出来，再写一遍只是白白序列化 7 次；
- 更重要的是，如果某个集合解析失败被回退成空数组，旧代码会在挂载后立刻把空数组写回，等于销毁原始数据。跳过首次写入后，坏数据仍留在存储里，可以用「导出原始数据」救回来。

变更写入交给 `storage/writer.ts` 的队列合并（默认 200ms）：

- 同一个集合在窗口内改多次，只写最后一次的值；一次操作改动多个集合时合成一批；
- 定时器只在第一批变更进来时启动，后续变更不会重置它 —— 连续编辑最坏也是每 200ms 落盘一次，不会无限推迟；
- 会强制 flush 的时机：`pagehide`、`visibilitychange` 变为 hidden（手机切后台可能被回收）、组件卸载、跨标签页同步读取之前、错误边界导出原始数据之前。

### 3.4 备份边界

| 集合 | 上限 | 依据 |
| --- | --- | --- |
| 记录 | 20 000 | 每天一班可记 54 年 |
| 排班 / 完成历史 | 各 20 000 | 同上 |
| 工资结算 | 1 200 | 100 年 |
| 单月调整项 | 200 | 正常月份个位数 |
| 文件体积 | 5 MB | 与设置页提示一致 |

超限直接报错并说明是哪一类，不静默截断——静默截断会让人以为数据导入成功了。

## 5. 后续可改进方向

1. **虚拟列表 / 分页游标**：记录过万后，首页即使分批渲染，`groupByDate` 仍会处理全部记录；可改为按月分页查询。
2. **IndexedDB 迁移**：localStorage 单键 5 MB 上限，记录量再上一个量级需要换存储引擎，并保留一次导出兼容层；届时写盘队列可以改为按 key 增量写，不必整集合序列化。
3. **增量序列化**：当前合并的是「写入时机」，每次仍是全量 `JSON.stringify`；记录很大时可以只序列化变化的集合（已经分集合写入）甚至做差量。
4. **组件层拆分**：`RecordSheet` / `PlanSheet` 仍有 400+ 行，可把「班次选择 / 时间 / 计薪预览」拆成独立区块组件。
5. **交互增强**：日历长按拖选多日、统计页区间对比、导出月报图片（2.2 已列为待办）。
6. **可观测性**：目前只有 `console.error` 与错误边界，可加一个本机「诊断日志」面板，记录存储异常、写盘失败与导入失败次数。
